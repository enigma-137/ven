Your .env, in order.

VEN keeps every project's environment variables in one encrypted vault on your machine, and shares them with your team from the terminal. Nobody needs to paste secrets into chat again.

Install

One command. It downloads the latest release, checks its checksum and puts ven on your PATH. You don't need Go or Node.

curl -fsSL https://ven.traceiq.run/install.sh | sh
irm https://ven.traceiq.run/install.ps1 | iex

Check it worked:

ven version
Other ways to install

Download by hand. Pick the archive for your system on the releases page, unpack it and move ven (or ven.exe) somewhere on your PATH. SHA256SUMS lists the checksums.

Build from source (needs Go 1.26+, and Node 20.19+ for the dashboard):

git clone https://github.com/enigma-137/ven
cd ven
make build        # bin/ven, dashboard included

Pin a version: VEN_VERSION=v0.2.0 before the install command. Change the folder: VEN_INSTALL_DIR=/usr/local/bin.

Windows builds aren't code-signed yet. If Windows 11's Smart App Control is on, it blocks ven.exe ("An Application Control policy has blocked this file"). Leave it on and use WSL for now. Older Windows may show SmartScreen instead: "More info" → "Run anyway".

Code signing: VEN has applied to the SignPath Foundation for free code signing of its Windows releases. See the code signing policy.

Quick start: just you

Everything stays on your computer. No account, no network.

  1. Create your vault and choose a master password (10+ characters). VEN also shows a one-time recovery key: save it in a password manager or on paper.

    ven init

  2. Make a project. It comes with development, staging and production.

    ven projects create "Billing API"

  3. Bring in an existing .env. VEN shows what's new or changed before saving.

    ven import .env -p billing-api -e development

  4. Write it back out whenever you need a file.

    ven export -p billing-api -e development --out .env

  5. Prefer clicking? Open the dashboard.

    ven ui
Forgot your master password? ven password reset with your recovery key sets a new one, and every value is still there. Without the password and the recovery key, nobody can decrypt the vault, including us.

Quick start: your team

  1. Log in with GitHub. The first time, you also choose an account password and get an account recovery key to save.

    ven login

  2. Create a shared project.

    ven remote create "Billing API"

  3. Link your project folder so you don't have to type the names again.

    ven link billing-api -e development

  4. Upload your .env, encrypted on your machine.

    ven push

  5. Invite a teammate by their GitHub username. Send them the code it prints.

    ven share --to octocat --env development

  6. Your teammate installs VEN, then:

    ven login
ven join ven_inv_…
ven link billing-api -e development
ven pull

Already have a project in your local vault? Upload it in one go with ven remote publish billing-api.

Projects & environments

A project is one app or service. Each project has environments such as development, staging and production, and each environment holds its variables.

  • Refer to them by name or by slug: "Billing API" and billing-api both work.
  • Shared projects are named owner/slug, e.g. octocat/billing-api. If the slug alone is unique for you, that's enough.
  • Every environment has its own key. Access to development never gives access to production.
ven projects list
ven envs create preview --project billing-api
ven envs rename preview review --project billing-api

Import

Read a dotenv file into an environment. Nothing in it is executed or expanded. Broken lines are reported by line number, never with their values.

ven import .env -p api -e development                  # add new keys, update changed ones
ven import .env.prod -p api -e production --replace    # also remove keys not in the file
ven import .env -p new-app -e dev --create             # create the project/environment if missing
ven import .env -p api -e staging --dry-run            # preview only

If a key already has a different value, VEN asks what to do, or you decide up front with --on-conflict overwrite or --on-conflict keep.

Export

ven export -p api -e development --out .env      # write a file (asks before overwriting)
ven export -p api -e development --stdout        # print, for pipes

Exported files contain plaintext. They're written with owner-only permissions, and VEN never overwrites a file without --force or your confirmation.

Get, set, list

ven list -p api -e development                 # names and types, values hidden
ven get STRIPE_KEY -p api -e development       # print one value
ven set STRIPE_KEY -p api -e development       # asks for the value, hidden
ven unset STRIPE_KEY -p api -e development

Values are typed secret or text, which only changes how they're shown. Every value is encrypted either way.

Dashboard

ven ui opens a local dashboard in your browser for browsing, editing, importing and exporting. It only listens on your own computer (127.0.0.1) and locks itself after 15 minutes of inactivity. Change that under Settings.

The dashboard shows your local vault. Shared projects are managed from the terminal for now.

Log in

ven login shows a short code. Open the link, type the code on GitHub and approve. VEN asks GitHub for no permissions: it only learns your username.

The first time, you choose an account password. It unlocks your account key, which is what actually decrypts shared environments. It never leaves your machine, and neither VEN nor GitHub can reset it. You also get an account recovery key (VENA-…) that can: save it somewhere safe.

ven login
ven whoami                  # your username and key fingerprint
ven account recover         # forgot the account password: use your recovery key
ven account recovery-key    # make a new recovery key
ven logout                  # ends this device's session
GitHub proves who you are. Your account password protects what you can read. Someone who steals your GitHub login still can't decrypt anything.

Push & pull

ven pull                              # decrypt into .env
ven pull --out .env.staging -e staging
ven pull --stdout | some-tool

ven push                              # upload .env (keys missing from the file are removed)
ven push --from .env.staging -e staging
ven push --merge                      # only add and update

Before uploading, push lists which keys are added, changed and removed (never values) and asks to confirm. If someone pushed in the meantime, VEN refuses so nobody's change is lost: pull, reapply yours, push again.

ven link writes .ven.json in your folder (project and environment, no secrets, safe to commit) and adds .env to .gitignore.

Run without a file

The safest way to use secrets: hand them straight to your app and leave nothing on disk.

ven run -- npm run dev
ven run -e staging -- ./deploy.sh

Or load them into your current shell:

eval "$(ven shellenv)"
ven shellenv | Invoke-Expression
ven shellenv --shell fish | source

Need one value somewhere else? ven copy STRIPE_KEY puts it on your clipboard (ven copy alone copies the whole environment).

Share & join

ven share --to octocat --env development,staging
ven share --to octocat --env development --role developer --expires 90d

That prints an invite code (ven_inv_…). Send it any way you like. It's safe in chat because it:

  • only works for that one GitHub account,
  • works once, and expires after 24 hours (--invite-ttl to change, up to 7 days),
  • carries the keys locked to a secret that only exists inside the code. The server can't open them either.

Your teammate runs ven join <code>. See and cancel unused invites with ven invites and ven invites revoke <id>.

RoleCan
viewer (default)Pull the environments they were given
developerAlso push changes
adminAlso invite, remove, approve and create tokens
ownerAlso delete the project

Members

ven members                              # who has access, to what, until when
ven members renew octocat --for 30d      # extend (or --for never)
ven members role octocat developer
ven members remove octocat --yes

Access lasts 30 days by default, then ends on its own. When someone is removed or expires, VEN changes the keys of the environments they could read, and nobody can push new values until that's done. members remove does it right away.

Removing someone stops future access. Anything they already pulled, they still know, so change those secrets at the source too (Stripe, AWS, …). ven audit shows what they pulled.

Protected environments

Environments named production, prod or live are protected (add more with --protect or ven remote envs create --protected). An invite code alone never unlocks them.

  1. Your teammate joins and runs ven whoami. It shows a fingerprint like K7QF-2M9X-….

  2. You run:

    ven members approve octocat

  3. Compare the fingerprint VEN shows you with theirs, on a call or in person. Approve only if they match.

This stops anyone, even a hacked server, from slipping in their own key instead of your teammate's.

CI & service tokens

Give CI jobs and servers their own read-only access instead of a person's login.

ven tokens create --name github-actions --env production --expires 90d

The token is shown once. Store it as a secret in your CI, then:

VEN_SERVER=https://ven.traceiq.run VEN_TOKEN=ven_st_… ven run -- ./deploy.sh
GitHub Actions example 
- name: Install VEN
  run: curl -fsSL https://ven.traceiq.run/install.sh | sh
- name: Deploy
  env:
    VEN_SERVER: https://ven.traceiq.run
    VEN_TOKEN: ${{ secrets.VEN_TOKEN }}
  run: ~/.local/bin/ven run -- ./deploy.sh

Tokens can't push, invite or create other tokens, and they always expire (one year at most). ven tokens shows when each was last used. ven tokens revoke github-actions ends one and changes the keys it had.

Audit log

ven audit
ven audit --limit 200

Admins see who pulled, pushed, shared, approved, removed or rotated what, when and from which IP. The log never contains values.

How it stays secret

1Your machine encryptsValues are locked with a key that never leaves your device unencrypted.
2The server stores noiseNo values, no variable names, no private keys, no invite secrets.
3Teammates decrypt locallyEach one opens the environment key with their own account key.
WhatHow
ValuesAES-256-GCM, a fresh random nonce on every write
Passwords → keysArgon2id (64 MiB, 3 passes)
Sharing keysX25519 + HKDF-SHA256, each environment key sealed to each person
TamperingEvery ciphertext is bound to its project, environment, version and owner, so moving it around fails
Sessions1-hour access tokens; refresh tokens work once, and reusing one logs that session out everywhere

All cryptography comes from Go's standard library and x/crypto; VEN doesn't invent its own. Full detail in the design document and security model.

VEN hasn't had an external security review yet. Treat it as a preview for anything critical. Found a problem? See SECURITY.md.

If something leaks

LeakedWhat happens
An invite codeNothing, unless the attacker is also logged in as that exact GitHub user before it's used or expires.
Your GitHub accountThey see project names and members, not values. They'd still need your account password.
The VEN serverCiphertext only. Weak passwords could be guessed offline, slowly, so use a strong one.
A service tokenRead access to its environments until you revoke it. Revoke it and change those secrets at the source.
A recovery keyLocal (VENR): together with a copy of your vault file, it opens the vault, so make a new one with ven password recovery-key. Account (VENA): together with your GitHub login, it opens your account key, so make a new one with ven account recovery-key.
A teammate leavesRemove them; keys change automatically. Change anything they pulled at the source.

Self-host

The server is the same ven program. It stores everything in one SQLite file and is light enough for a small VPS.

  1. Create a GitHub OAuth App (Settings → Developer settings → OAuth Apps) and tick Enable Device Flow. Copy the Client ID; no secret is needed.

  2. Run the server on loopback, behind a reverse proxy that does HTTPS (Caddy, nginx):

    ven server --db /srv/ven/server.db --github-client-id Ov23… --trust-proxy

  3. Point everyone at it:

    ven login --server https://ven.yourcompany.com

A ready systemd unit, Caddy block, backup script and step-by-step guide are in deploy/.

Troubleshooting

I forgot my password

Master password (local vault): run ven password reset and enter your recovery key (VENR-…). Your values are untouched.

Account password (teams): run ven account recover and enter your account recovery key (VENA-…). Your access is kept.

Lost the recovery key too? The local vault can't be opened. For teams, ven login --reset-key gives you a new account key; admins then share with you again, and the team loses nothing.

I never got a recovery key

Vaults and accounts created before recovery keys existed don't have one. Make one now: ven password recovery-key for your local vault, ven account recovery-key for your team account. ven status shows whether your vault has one.

"waiting for approval"

The environment is protected. Ask an admin to run ven members approve <you>, and read them your ven whoami fingerprint.

"changed since you last pulled"

Someone pushed first. Run ven pull, reapply your change, then ven push.

"key must be rotated"

Someone lost access. Any developer or admin with access fixes it by running ven pull, which changes the key automatically, or ven remote rotate.

"invite not found"

The code expired, was already used, was revoked, or you're logged in as a different GitHub account than the one invited. Check ven whoami, then ask for a new invite.

Windows blocks ven.exe

"An Application Control policy has blocked this file" comes from Smart App Control (Windows Security → App & browser control → Smart App Control). It blocks apps that aren't code-signed, and VEN's Windows builds aren't signed yet. Don't turn it off: Windows can't turn it back on without a reinstall. Run VEN in WSL instead; Smart App Control doesn't apply there:

wsl --install                                   # PowerShell as admin, once; restart
curl -fsSL https://ven.traceiq.run/install.sh | sh   # then inside Ubuntu
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc && source ~/.bashrc

Your Windows folders are under /mnt/c/, e.g. cd /mnt/c/Users/you/project && ven pull.

On a work PC, the same message can come from a company policy: ask your IT team to allow ven.exe.

"Windows protected your PC" is SmartScreen: click "More info" → "Run anyway".
